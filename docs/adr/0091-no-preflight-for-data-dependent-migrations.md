# 0091. データ依存のマイグレーションに事前検証を設けない

- Status: Accepted
- Date: 2026-11-20
- Deciders: ptiringo

## Context（背景・課題）

本番（Cloud Run）は、アプリの起動時に Flyway がマイグレーションを流す（`spring.flyway.enabled: true`）。デプロイは main への push で `deploy.yml` が自動的に走る。

そのため、既存データに依存して失敗しうるマイグレーション（UNIQUE / CHECK / FK / NOT NULL の遡及追加や `VALIDATE CONSTRAINT`）は、デプロイして初めて失敗が分かる。#602 は、デプロイ前に「本番データが新しい制約を満たすか」を確かめる手段を用意するかを問うた。実例は 2 件ある（#544 / PR #600 の UNIQUE 追加、#983 / PR #993 の CHECK の VALIDATE）。どちらも事前に確かめたから通ったのではなく、アプリが書く行が常に整合していたから、結果的に通っただけである。

起票時は、失敗すると「Flyway が failed を記録し、復旧には本番 DB への手動 SQL（`flyway repair`）が要る」と想定していた。

### 失敗したときに何が起きるかの実測（2026-11-19）

本番と同じ Flyway 12.4.0 と、使い捨ての PostgreSQL 17 で再現した。

| ケース | 失敗したとき | 直して流し直すと |
| --- | --- | --- |
| UNIQUE の追加（重複行あり） | ロールバックされ、`flyway_schema_history` に failed の行は残らない | マイグレーションのファイルを直すだけで通る。repair は要らない |
| CHECK の `VALIDATE CONSTRAINT`（違反行あり） | 同上 | 同上 |
| `CREATE UNIQUE INDEX CONCURRENTLY`（非トランザクション） | 履歴に failed の行は残らないが、INVALID な索引が残る | 直しても `relation ... already exists` で阻まれる。残骸を消す `DROP INDEX CONCURRENTLY IF EXISTS` を同じファイルに書くと、Flyway 自身が開いたままにしている接続（`idle in transaction`）を待って止まった |

PostgreSQL は DDL もトランザクションで巻き戻せるので、トランザクション内で流れるマイグレーションは、失敗しても何も残らない。このプロジェクトのマイグレーションは、すべてトランザクション内で流れる（`CONCURRENTLY` は使っていない。[ADR-0062](0062-unique-backstop-plain-add-constraint.md)、`.claude/rules/migrations.md`）。

また、失敗したときの影響も、起票時の想定より小さい。

- **本番は止まらない**: `deploy-cloudrun` は、新しいリビジョンが起動しなければトラフィックを切り替えない。古いリビジョンが動き続け、止まるのはそれ以降のデプロイだけである。
- **失敗に気づける**: デプロイが失敗すると、GitHub Issue が自動で立つ（[ADR-0089](0089-production-monitoring-uptime-and-deploy-failure.md)）。

### 検討した案

- **プレフライト SQL を PR に書く運用**: PR #600 で行ったこと。軽いが、人の規律に頼る。PR #993 では実際に書かれなかった。
- **CI ジョブで本番データの違反行数を数える**: viewer SA で本番 DB に読み取りで接続する。Prisma Postgres への接続経路と資格情報を CI に渡す必要があり、検査する SQL を制約の種類ごとに組み立てる仕組みも要る。
- **起動時の migrate をやめ、独立したジョブで先に流す**: 最も筋が良いが、最も重い。上の実測のとおり、今は失敗しても本番が止まらないので、得られるものが小さい。
- **何もしない**

## Decision（決定）

**データ依存のマイグレーションに、事前検証の仕組みを設けない。** 失敗したら、直して出し直す。

失敗したときの戻し方:

1. デプロイ失敗の Issue で気づく。本番は古いリビジョンのまま動いている。
2. 失敗したマイグレーションは適用されていないので、ファイルを書き換えてよい（チェックサムに引っかからない）。違反している行を直す UPDATE を同じマイグレーションに足すか、制約の定義を直す。
3. main に入れて出し直す。repair も、本番 DB への手動 SQL も要らない。

## Consequences（結果・影響）

- 守りは、アプリが書く行が常に整合していること（自己検証ファクトリとマッパー）に頼る。壊れうるのは、アプリ以外の経路で書かれた行（手動 SQL、過去のバグで入った行）があるときで、そのときはデプロイが失敗して初めて分かる。
- 1 回の起動で複数のマイグレーションを流すと、成功した分は確定する。途中で失敗すると、たとえば `NOT VALID` の制約だけが入った状態で止まる。後続のマイグレーションを直して出し直せば揃う。
- 違反している行の直し方（消すのか、値を補うのか）は、失敗してから決めることになる。データの意味に関わる判断なので、事前検証があっても避けられない。
- **再評価のきっかけ**: `CREATE INDEX CONCURRENTLY` などの非トランザクションのマイグレーションを使い始めるとき（INVALID な索引が残り、手動の `DROP INDEX` が要る。ADR-0062 の再評価トリガと同じ）。または、アプリ以外の経路で本番データを書き換えるようになったとき。
- ADR-0062 の「失敗するとマイグレーションが failed 状態のまま残る」は、Flyway 12.4.0 の実測とは異なる。残るのは INVALID な索引で、履歴に failed の行は残らない。どちらにしても手動の後始末が要るという、ADR-0062 の結論は変わらない。
