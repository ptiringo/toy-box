# 0089. 本番の監視をサービス停止とデプロイ失敗の検知から始める

- Status: Accepted
- Date: 2026-11-01
- Deciders: ptiringo

## Context（背景・課題）

本番は Cloud Run と Prisma Postgres で動いているが、アプリの稼働監視がない。Actuator は `/actuator/health` だけを公開し、メトリクスの export もない。既存のアラートは、人間による GCP の変更操作を検知するもの（[ADR-0078](0078-audit-via-admin-activity-detect-only.md)）だけである。

監視が必要な場面は、実例と確認結果から次の 2 つが挙がっている。

- **デプロイ失敗の放置**: 2026-10-23〜24 に、main のデプロイ失敗に約 19 時間気づかなかった。アプリは旧版のまま動いていたので、ヘルスチェックやエラー率では検知できない。
- **DB の停止**: Prisma Postgres は operations が枠を超えると読み書きを拒否する（[ADR-0074](0074-billing-guardrails-spend-cap-and-budget-alert.md)）。GCP の budget alert はこれでは鳴らない。

検討の途中で、もう 1 つの関心として不正利用の検知が挙がった。これは API が正常に応答している間に起きるので、停止の監視では見つからず、見る項目も別になる。そこで切り離し、#1017 で検討する。

### 検討して採らなかった案

- **エラー率・レイテンシの監視**: 一部の API だけのエラーに気づけるが、個人の sandbox でアクセスが少なく、割合のしきい値が安定しない。
- **ダッシュボード**: 見に行かない間に起きたことには気づけない。
- **メトリクスの export（Micrometer、`/actuator/prometheus` の公開）**: 上記を作らないなら、使い道がない。
- **定期レポートだけで済ませる**: 次の配信まで停止に気づけない。不正利用の検知の候補として #1017 に残す。

## Decision（決定）

**サービス停止とデプロイ失敗の 2 つを検知する。** それ以外の監視は、必要になった時点で追加する。

- **サービス停止**: Cloud Monitoring の uptime check で `/actuator/health` を確認し、失敗したらメールで通知する。確認間隔は 15 分（決定時点の値。現行値は実装後の `infra/` を参照）とする。
- **デプロイ失敗**: `deploy.yml` の main での失敗を別のワークフローで受け、GitHub Issue を自動で立てる。別のワークフローにするのは、GCP の認証やビルドで落ちた場合も拾うためである。Issue にすれば、次の作業を選ぶときの候補にも残る。

実装は #1018（uptime check）と #1019（デプロイ失敗）で行う。

## Consequences（結果・影響）

- 停止に気づくまで、15〜30 分ほどかかる見込みである。すぐに知る必要はないと判断した。
- 次のものは検知できない。一部の API だけのエラー、レイテンシの悪化、Prisma の枠に近づいたこと（超過で止まった後なら検知できる見込み）。枠の消費の事前把握は #1017 の定期レポートと合わせて検討する。
- uptime check を置くと、費用と DB の消費が増える。Cloud Run は `--min-instances=0` なので、確認のたびに起動し直す可能性がある。3 地点から確認するなら月に約 8,600 回で、1 回を 1 operation と仮定すると Prisma の枠（決定時点で 200,000 operations/月）の約 4% にあたる。
- Cloud Run は `--no-allow-unauthenticated` なので、uptime check にも呼び出し権限と認証が要る。

### この決定の前提で、未確認のもの

次の点は実装時に確かめる。想定と違えば、この決定を見直す。

- `/actuator/health` が DB へ問い合わせているか。問い合わせていなければ、DB の停止を検知できない。
- その問い合わせが Prisma の operations に数えられるか。
- コールドスタートが uptime check の制限時間に収まるか。収まらなければ誤報になる。
- デプロイ失敗の Issue の作成通知に気づけるか。10 月に GitHub の標準通知で気づけなかった理由は調べていない。

## 追補（2026-11-02）: uptime check の実装（#1018）で分かったこと

方針は変えていない。実装の形と、上の未確認事項の結果を記録する。

### 実装の形が想定と違った点

- **監視対象は `uptime_url` ではなく `cloud_run_revision` にした**。サービスエージェントの OIDC 認証を `uptime_url` に付けると、API が 400 で拒否する。
- **証明書の検証（`validate_ssl`）は有効にしていない**。`uptime_url` でしか使えない。Cloud Run の URL は Google が管理する証明書を使うので、影響は小さいと判断した。
- **呼び出し権限は足していない**。Monitoring のサービスエージェントのロール（`roles/monitoring.notificationServiceAgent`）に `run.routes.invoke` が含まれている。
- **`/actuator/health` では Bearer トークンを検証しない**。uptime check は Cloud Run を通るために Google の ID トークンを載せてくる。Spring の Bearer 検証は認可判定より前に走るので、`permitAll` でも発行者の違いで 401 になった。専用のフィルタチェーンで検証を外した（`SecurityConfig`）。Cloud Run の IAM は引き続き効いている。

これらはいずれも `plan` では検出できず、apply するか実際に check を動かして初めて分かった。

### 未確認事項の結果

- **DB への問い合わせ**: `/actuator/health` の結果には DB の状態が含まれる（`HealthEndpointTest` で固定）。
- **コールドスタート**: 制限時間 60 秒（決定時点の値。現行値は `infra/modules/uptime/main.tf`）に収まっている。起動を伴った初回の応答は 12〜19 秒だった。
- **起動の頻度**: 「確認のたびに起動し直す」想定は外れた。2026-11-01 21:42Z から約 15 時間で、アプリの起動は check 作成直後の 2 回とデプロイの 3 回だけだった。3 地点の確認がずれて届くので、インスタンスが落ちずに残っている。
- **発火と通知**: 上記の 401 が続いた間にアラートが発火し、メールが届いた。修正のデプロイ後に応答が 200 へ変わり、障害は自動で閉じた。実際の停止ではなく 401 による発火だが、check の失敗から通知までの経路は同じである。

### まだ確かめていないこと

- **Prisma の operations**: uptime check の問い合わせが数えられるかは測っていない。#1017 の枠消費の把握と合わせて見る。
- **Cloud Run の費用**: 請求額では確かめていない。CPU を常時割り当てにしていないので、1 日 288 回、1 回 0.3 秒以下の応答なら増加はわずかと見込んでいる。
