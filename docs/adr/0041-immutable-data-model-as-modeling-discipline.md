# 0041. イミュータブルデータモデルを永続化機構ではなくモデリング規律として部分採用する

- Status: Accepted
- Date: 2026-06-30
- Deciders: Matsui

## Context（背景・課題）

永続化スタイルとして、kawasima 氏の「イミュータブルデータモデル」（出典: <https://scrapbox.io/kawasima/イミュータブルデータモデル> ）の採用可否を評価したい（Issue #444）。

要旨:

- CRUD のうち UPDATE が最もシステムを複雑にする（更新ルールがテーブル定義から読み取れず画面/バッチ設計書に散らばる）。UPDATE の発生そのものを減らすようデータモデルを設計する。
- エンティティを **リソース**（実体・マスタ的。Who/What/When/Where）と **イベント**（業務上起きた事実。「〜する」が成り立つ。Why/How）に二分する。基準は「属性に “日時” を持つか」。
- **イベントは日時属性を 1 つだけ持ち INSERT-only**。複数日時を持つテーブルは分解する。
- **ロングタームイベントパターン**: 始点終点を持つ長期プロセスは「現在ステータスを保持する親 ＋ INSERT-only 詳細イベント子テーブル」で表す。**現在ステータスは親行に格納し UPDATE する**。
- 一律の created/updated 付与は禁止（updated を付けたくなったら隠れたイベントの試験薬）。削除フラグは忌避し区分（subtype/判別子）で表す。

評価上の重要な区別として、**append-only は「イベント」エンティティの性質であって、データベース全体の性質ではない**。リソース（ロングタームイベントのスーパータイプを含む）は現在状態を格納し UPDATE される。「全イベントを畳み込んで現在状態を都度導出する」のはフルのイベントソーシング（ES）であり、イミュータブルデータモデルそのものではない（この手法は現在状態を格納する点で既に ES とフル mutable の中間に位置する）。

本プロジェクトの接点:

- ドメイン集約は既にイミュータブル（[0009](0009-immutable-aggregates.md)、状態遷移＝新インスタンス返却）。
- 「起きたこと」を `StateTransition` ＋ドメインイベントで一級市民化済み（[0029](0029-domain-events-via-state-transition-return.md)）。ただし実装は `HorseNamed` のみで、retire / recordFoaling 等は未イベント化。
- 一方、**永続化層は 1 集約 = 1 行の UPDATE 上書き前提**（`@Version` は楽観ロック用。update 経路自体は #424 で未実装）。
- sealed バリアントは判別子 + フラット列 + CHECK で表現（[0020](0020-sealed-origin-and-discriminated-origin-subobject.md)）。読み取りは軽量 CQRS L2（[0031](0031-lightweight-cqrs-read-model.md)）。

すなわち「ドメインは既に append 寄りなのに、永続化層は UPDATE 上書き」というギャップがある。これをイミュータブルデータモデル流にどこまで埋めるかが論点。

### 検討した代替案

- **A. 不採用**: 1 集約 = 1 行・UPDATE 上書き ＋ `@Version` を継続し、状態遷移もすべて現在状態行の更新で表す。監査・履歴はドメインイベントで補う。コストは最小だが、ドメイン（不変）と永続化（可変）のギャップが残り、テーブル設計指針（#443）に与える分類軸が宙に浮く。
- **C. 全面採用**: 全集約を厳密にリソース/イベント分類し、あらゆる状態変化を INSERT-only イベント化、ロングタームイベントを徹底する。探索 sandbox・少数集約には過剰で、子テーブル分割と楽観ロックの再設計コストが大きい。
- **B. 部分採用（採用）**: 後述。

## Decision（決定）

イミュータブルデータモデルを「**永続化の一律機構**」ではなく「**モデリングの規律・語彙**」として**部分採用**する。

**採用する:**

1. **リソース/イベントの分類**を設計語彙として導入する（集約・テーブル設計時に R/E を意識する）。テーブル設計指針（#443）の分類軸の中核に据える。
2. **イベントは INSERT-only・日時 1 つ**。真にイベント性のある事実（種付 Covering・分娩 Foaling・命名 HorseNamed・退役 Retired 等）はイベントとして記録し、既存のドメインイベント（[0029](0029-domain-events-via-state-transition-return.md)）と対応づける。
3. **ロングタームイベントパターン**を採用する。始点終点を持つ長期プロセス（繁殖成績の covering→foaling ライフサイクル等）は「現在ステータスを持つ親 ＋ INSERT-only 詳細イベント子テーブル」で表し、**現在ステータスは親行に格納して UPDATE する**。
4. **一律 created_at/updated_at の付与を禁止**する。updated_at を付けたくなったら、その裏にある隠れたイベントを抽出する。
5. **削除フラグ/論理削除を忌避**し、状態は区分（判別子/subtype）かイベントで表す。

**採用しない（明示的に線引きする）:**

1. **フルのイベントソーシング**（全イベント畳み込みで現在状態を都度導出する）。現在状態は格納する。
2. **リソースの append-only 化**。リソースは現在状態行のまま UPDATE 可とし、`@Version` 楽観ロック（#424）を併用する。
3. **世代（未来日付の適用期間）パターン**は現状不要（YAGNI）。要件が出たら別途評価する。

**判断基準（どの状態遷移をイベントテーブルに切り出すか）:**

- その遷移が**業務上の独立した事実**で、発生時刻・付随属性を記録する価値があるか（＝ドメインイベントを既に返している／返すべきか）。Yes ならイベントテーブル候補。
- 単なる属性の現在値の差し替え（名前の typo 修正レベル）なら現在状態行の UPDATE で十分。
- コレクション（BreedingResult の `Covering` 等）は元々子テーブルが要るため、自然にイベント子テーブル化できる。

## Consequences（結果・影響）

- **得られるもの**: ドメインのイミュータブル（[0009](0009-immutable-aggregates.md)）と「起きたことの一級市民化」（[0029](0029-domain-events-via-state-transition-return.md)）を永続化層の設計規律へ延長でき、ドメイン/永続化のギャップに一貫した語彙を与えられる。append-only はイベントテーブルに限定されるため、ES の読み取り再設計（プロジェクション/畳み込み）コストを負わない。
- **引き受けるもの**: 真にイベント性のある遷移では「1 集約 = 1 行」から「現在ステータス親行 ＋ イベント子テーブル」へのテーブル設計変更が生じる（`@MappedCollection` 等、#443 のコレクション設計と直結）。当面は段階移行とし、新規モデリング（繁殖成績 covering/foaling 等、#455-#457）からこの規律を適用する。既存の単一行テーブル（`jockey` / `blood_horse`）の遡及変更は実需が出るまで行わない。
- **既存 ADR との関係**: [0009](0009-immutable-aggregates.md) / [0029](0029-domain-events-via-state-transition-return.md) を補完する。[0020](0020-sealed-origin-and-discriminated-origin-subobject.md)（sealed 判別子）とも両立する。
- **フォロー先**: 本決定の具体適用は #443（マッピング指針。R/E 分類・「日時 1 つ」・ロングタームイベントの親子分割を指針の中核へ。フラット+判別子 vs 子テーブルの使い分け基準に「イベント性があるか」を加える）と #424（更新するのはリソース/ロングタームイベント本体のみという制約。イベントは INSERT-only ＝楽観ロック不要）に委ねる。
