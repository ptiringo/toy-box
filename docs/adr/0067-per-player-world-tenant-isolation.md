# 0067. プレイヤーごとの世界によるテナント分離

- Status: Accepted
- Date: 2026-08-06
- Deciders: ptiringo

## Context（背景・課題）

Issue #703（IAM: アカウントと世界）で、フロントエンドをシミュレーションゲームとして作り直すことに
なった。この結果「プレイヤーが自分の箱庭（セーブデータ）の中で全操作を行う」という前提が生まれ、
これが既存の認可設計の土台を崩した。ADR-0064 は「認証は Identity Platform、認可の権限は自前 DB に
持つ」という骨格を決めたが、`Actor` をどのリングに置き、認可を何で判断するかは「別の ADR に記録する」
として明示的に持ち越していた。本 ADR がその持ち越し分にあたる。

### ロールベース認可（`REGISTRAR` / `BREEDER` / `VIEWER`）を採らない

当初検討していたロールベース認可は、複数の利用者が同じデータ（例: JAIRS の登録原簿相当）を共有し、
役割によって操作範囲を分ける前提のものだった。ゲームのプレイヤーは自分の世界の外を一切触らず、
世界の中では登録・更新・削除の全操作を単独で行う。この前提でロール表を作ると、行が実質 1 種類
（全操作を許すロール）だけに縮退し、「全員が同じ権限を持つだけの表」になって存在理由を失う。認可の
主軸は「その人が誰か（ロール）」から「そのデータが誰のものか（所有）」へ移った。ADR-0064 の骨格は
維持しつつ、自前 DB に持たせる中身をロール・権限から世界の所有関係へ差し替える。

### テナントの単位: アカウントではなく世界（セーブデータ）

テナント分離の単位として「アカウント」と「世界」の 2 案を検討した。

- **アカウント単位**: 1 アカウント＝1 テナント。各テーブルに `account_id` を 1 本足すだけで済み実装は
  単純だが、1 プレイヤーが複数のセーブデータ（例: やり直し用の別牧場）を持てない。後から
  「アカウントは複数の世界を持てる」へ変えると、全テーブルの `account_id` 列を `world_id` へ
  差し替えるマイグレーションをやり直すことになる。
- **世界単位**（採用）: `Account` は複数の `World` を持て、世界ごとに独立してリセット・削除できる。
  最初から世界を挟むことで、後からの引っ越しコストを払わずに済む。

### 世界にドメイン種別（`kind`）を持たせない

`World` に `kind: StudbookOrRacing` のようなドメイン種別を持たせ、コンテキストごとに世界を使い分け
させる案も検討したが採らない。対象ドメインは studbook / racing に限らず sakamichi / tennis も含む
全コンテキストであり、`iam` がこの種別を持つと `iam` が全コンテキストの語彙を知ることになる。新しい
コンテキストを追加するたびに `iam` を変更する必要が生まれ、コンテキスト間の依存禁止という規約と
対立する。プレイヤーがドメインごとに世界を使い分けたい場合は、世界を複数作って名前で区別すればよく、
`World` 自体は「誰のものか」「名前」だけを持つ、ドメインに無関心な形にとどめる。

### `World` 集約を `iam` に置く

`World` をどのコンテキストに置くかも論点だった。この API の唯一の認可判断は「この世界はあなたの
ものか」であり、これは `Account` と `World` の所有関係そのものである。`World` を別のコンテキストへ
切り出すと、唯一の認可判断がコンテキストをまたぐことになり、DB 上はスキーマ間 FK
（ADR-0048 のコンテキスト別スキーマ分離と対立）になる。`Account` と `World` は不可分の 1 つの判断を
支える 1 組の集約として、同じ `iam` コンテキストに置く。

### 世界のスコープを URL 階層（AIP-122 の親子リソース）で運ぶ

世界のスコープをリクエストへどう乗せるかも検討した。

- **`X-World-Id` ヘッダ**（却下）: リクエストに世界を明示させられるが、付け忘れてもリクエストは
  失敗せず「サーバ側の既定世界」等の隠れ状態へ暗黙に解決されうる。これは「別の世界に書き込んで
  しまう」事故を静かに許す。
- **サーバ側の「現在選択中の世界」をセッションで保持**（却下）: 同種の隠れ状態の問題に加え、
  API がステートレスでなくなる。
- **URL 階層（`/api/worlds/{worldId}/...`）**（採用・次段階で導入）: AIP-122 の親子リソース名の
  形式に沿い、リクエストごとに世界が URL 上に明示される。渡し忘れはルーティング不一致として
  即座に顕在化し、隠れ状態を持たない。

  > 追補（2026-08-08）: `#705` で全ドメイン API を `/api/worlds/{worldId}/...` 配下へ移設済み。

### 却下案: 世界ごとの DB スキーマ分離 / PostgreSQL RLS

テナント分離を DB 層で実装する案も検討した。

- **世界ごとの DB スキーマ分離**（却下）: ADR-0048 のコンテキスト別スキーマ分離と同じ発想を
  世界単位へ広げる案。世界はプレイヤーが自由に作成・削除するものであり、世界が増えるたびに
  Flyway マイグレーションが必要になる。数百・数千のスキーマを動的に生成・破棄する運用は非現実的。
- **PostgreSQL RLS（Row Level Security）**（却下）: セッション変数（例: `app.current_world_id`）を
  コネクション単位で設定する必要がある。この API はコネクションプール + Virtual Thread で動くため、
  「どのコネクションにどのセッション変数が設定されているか」がリクエストとコネクションの対応に
  依存し、設定漏れを機械的に防ぎにくい。設定漏れは「静かにデータが漏れる／消える」バグになり、
  対応の複雑さがバグそのものより厄介と判断した。

### 他人の世界を 403 ではなく 404 にする

他人の世界を指す `PATCH` / `DELETE` のレスポンスを 403 Forbidden と 404 Not Found のどちらにするかも
論点だった。403 は「リソースは存在するが、あなたには権限がない」という事実を暗に返す。プレイヤーの
箱庭では、他人の世界が存在すること自体を知らせる理由がない。したがって「存在しない」と「あなたの
ものではない」を区別せず、一律 404 `world-not-found` を返す。

## Decision（決定）

**認可の主軸をロールベースから所有ベース（テナント分離）へ切り替え、テナントの単位を「世界
（セーブデータ）」とする。`World` 集約は `iam` コンテキストに置き、Account : World = 1 : N の所有
関係だけを唯一の認可判断とする。**

今回実装したスコープは次のとおり。

- 共有カーネル（`domain.shared`）に `AccountId` / `WorldId`（いずれも `@JvmInline value class`）を
  置く（`src/main/kotlin/com/example/api/domain/shared/Tenancy.kt`）。ID は全コンテキストが読む
  横断的な値であり、コンテキスト間依存が全面禁止されている以上、置ける先は共有カーネルしかない。
- `iam` コンテキストに `Account` 集約（JWT の `sub` と 1:1）と `World` 集約
  （`accountId` / `name` のみを持ち、ドメイン種別を持たない）を置く。`World.isOwnedBy(accountId):
  Boolean` が唯一の認可判断を表現する（`src/main/kotlin/com/example/api/domain/iam/model/`）。
- `POST /api/me:provision` を新設し、初回ログイン時にアカウントと最初の世界（既定名）を冪等に作る
  （`ProvisionMeUseCase`）。ADR-0064 が「初回アクセス時の自動プロビジョニングは採らず、dev / test
  は Flyway seed で賄う」としていた点を、この決定で改める（プロビジョニング経路を確定させた）。
- `GET/POST/PATCH/DELETE /api/worlds`（AIP 標準メソッド）を新設し、`@CurrentAccount` で解決した
  `AccountId` に閉じた一覧・作成・改名・削除を提供する（`WorldController`）。他人の世界への操作は
  `World.isOwnedBy` の判定結果を経由して一律 404 `world-not-found` に潰す。
- JWT の `sub` から `AccountId` を解決する `CurrentAccountArgumentResolver`
  （`HandlerMethodArgumentResolver`）を追加する。未登録 subject は `AccountNotProvisionedException`
  → 403 `account-not-provisioned` として `GlobalExceptionHandler` が返す。
- 既存のドメイン API（`bloodHorses` / `jockeys` 等）とその永続化には手を付けていない
  （**次段階で世界スコープ化する**。下記「次段階」を参照）。

## Consequences（結果・影響）

- 「誰が何をしてよいか」という表を管理・維持するコストが消え、「そのデータは誰の世界のものか」だけ
  見ればよくなった。ロールの追加・変更に伴う認可ロジックの改修が不要になる。
- ADR-0042（外部公開 ID は当面生 UUID 据え置き）の再評価トリガが引かれた（詳細は ADR-0042 の
  追補を参照）。`world` という実在の親リソースが AIP-122 の親子リソース名を要求し、
  `/api/worlds/{worldId}/...` という URL 階層採用につながった。
- **認識している弱点**:
  - **読み取りのスコープ漏れは DB が守らない。** 次段階で入る複合 FK（`world_id` を含む外部キー）
    が止めるのは書き込み時の参照整合性だけで、`WHERE world_id = ?` を書き忘れた `SELECT` は
    そのまま実行され、他人の世界のデータが素通りして返る。読み取り側の防波堤は ArchUnit と
    契約テストに頼るしかなく、DB 制約による機械強制はできない。
  - **`@WebMvcTest` slice テストでは worldId の渡し忘れを捕まえられない。** slice は認証フィルタを
    無効化しているため（ADR-0064）、controller がユースケースへ worldId を渡し忘れるバグは
    slice テストを素通りする。コンパイル時の必須引数（Kotlin の非 null パラメータ）と E2E が
    backstop になる。
- **今回の実装で踏んだ罠（後続の実装者向け）**: Kotlin の `@JvmInline value class`
  （`AccountId` / `WorldId` 等）は、通常のメソッド引数として使われると JVM シグネチャ上は下敷きの
  型（`UUID`）へ消去される。`CurrentAccountArgumentResolver.supportsParameter()` を
  `parameter.parameterType == AccountId::class.java` と実装すると、実際のハンドラ引数
  （`@CurrentAccount accountId: AccountId`）は消去後 `UUID` になっているため**この比較は常に
  false になり resolver が一度も呼ばれない**（別の resolver が誤って引き取り NPE → 500 という
  形で顕在化する）。修正は消去後の実型（`UUID::class.java`）と比較すること。
  `.claude/rules/architecture.md` の「ArchUnit で Kotlin の呼び出しを縛るときの空振り」に記載されて
  いる value class のメソッド名マングリングと同根の事情であり、value class を Spring MVC のような
  フレームワークへ渡す箇所全般で再発しうる。
- **追補（#713 で解消）**: 上記の「`:provision` は冪等に作る」は、当初は**逐次実行に限った冪等**
  だった。実装は事前照会（`findBySubjectId` / `existsByAccountId`）→ insert の 2 手で、そのあいだに
  別リクエストが同じ subject を insert すると UNIQUE 制約違反（`uq_account_subject_id` /
  `uq_world_account_id_name`）が未捕捉のまま伝播して 500 になっていた。サインイン直後にフロント
  エンドが必ず 1 回叩く経路であり、StrictMode の二重発火・複数タブ・リロードで現実に踏む。
  `DuplicateKeyException` を捕まえて読み直す素直な対処は、PostgreSQL が UNIQUE 違反の時点で
  トランザクションを abort 済みのため同一トランザクション内では成立せず、別トランザクション境界の
  手当てを要した。#713 では**そもそも UNIQUE 違反を例外にしない**方針を採り、`INSERT ... ON CONFLICT
  DO NOTHING` ＋読み直しの専用ポート（`AccountRepository.saveIfAbsent` /
  `WorldRepository.saveIfAbsent`）へ寄せた。DB の UNIQUE を唯一の裁定者にすることで TOCTOU が結果に
  影響しなくなり、`:provision` は並行実行下でも冪等になった（事前照会は 2 回目以降の書き込みを避ける
  高速経路として残るだけで、正しさはこれに依存しない）。なお**利用者が名前を指定する世界の作成・改名
  は対象外**で、同名衝突を 409 として見せる必要があるため事前照会と `save` を使い続ける（そちらの
  TOCTOU は未解消のまま）。
- **次段階（本 ADR のスコープ外）**: 既存ドメイン（studbook / racing / sakamichi / tennis 全コンテキ
  スト）への `world_id` 列の追加・複合 FK の導入、既存 API の `/api/worlds/{worldId}/...` への移設は
  Issue #704 / #705 / #706 で扱う。本 ADR は「テナント分離の設計判断」を確定させるものであり、
  既存ドメインの世界スコープ化は未実装（「実装済み」ではない）。
