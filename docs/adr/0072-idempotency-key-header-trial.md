# 0072. Idempotency-Key ヘッダを 1 エンドポイントで試作する

- Status: Accepted
- Date: 2026-08-11
- Deciders: Matsui

## Context（背景・課題）

Issue #750。作成系 `POST` はネットワーク断・タイムアウト等でクライアントが再送すると、サーバ側では処理が
成功していてもリソースが二重に生まれうる。再送安全性を場当たりで各エンドポイントに実装するのではなく、
標準に寄せて API 全体の一貫性を上げたい。

再送安全性を運ぶ手段として 2 案を検討した。

- **IETF draft `Idempotency-Key` ヘッダ**（`draft-ietf-httpapi-idempotency-key-header-07`、
  2025-10-15 付。**Expired であり RFC 化されていない**）。値は RFC 8941 の Structured Header
  （String）で、処理済みの再送は前回の結果を返す SHOULD、処理中は 409、キー再利用（別ペイロード）は
  422 という骨格を示す。
- **Google AIP-155**（Request Identification）。`string request_id` を**リクエストボディ**に置く。
  optional にすべき（SHOULD）で UUID4 推奨、重複時は前回の成功レスポンスを返す SHOULD。

### AIP-155 を採らない理由

冪等キーは「同じ HTTP リクエストの再送」を識別するための情報であり、**リソースの表現ではなく転送レイヤの
関心**である。ADR-0021（リソース設計は AIP・エラー描画は RFC 9457 という系統の使い分け）と同型の切り分けで、
AIP-155 のようにリソース表現（ボディ）へ持ち込む案は採らない。ボディに混ぜないことでリクエスト DTO を
汚さずに済み、フロントは送信経路の 1 か所（ヘッダ付与）で全エンドポイントに対応できる。ボディを持たない
`DELETE` やカスタムメソッドへも同じ手を広げられる。加えて AIP-155 は処理中の 409 や指紋不一致の 422 を
一切規定しておらず、採用しても細部（本 ADR が扱う逸脱そのもの）は結局自分で決めることになる。

**ヘッダ側の拠り所（IETF draft）が Expired である事実は曖昧にしない。** 生きた標準ではなく、Stripe /
PayPal 等が採る**業界のデファクトプラクティス**として採用する、という位置づけで進める。

## Decision（決定）

**再送安全性は `Idempotency-Key` リクエストヘッダで受ける。AIP-155 の `request_id`（ボディフィールド）
は採らない。** 適用範囲は `POST /api/worlds/{worldId}/jockeys` の 1 本のみとする（試作）。

### 実装した挙動

- ヘッダは**任意**。付いていなければ従来どおり処理する。
- 同じキー・同じ内容（リクエスト DTO の SHA-256 指紋が一致）の再送は、初回と同じ結果を返す。ユースケースは
  記録済みの `resourceId` から集約を**読み直し**、初回と同じマッピング経路でレスポンスを組み立てる（別の
  レスポンス生成経路を持たない）。
- 同じキー・異なる内容（指紋不一致）は 422 `idempotency-key-reused` を返す。
- 記録は新設した `shared.idempotency_record` テーブル（主キー `(world_id, idempotency_key)`）が持つ。
  ドメインの概念ではなく再送というプロトコル上の事象を扱うため、コンテキスト別スキーマではなく
  横断的な `shared` に置く。ポートは `application/shared/idempotency`、実装は
  `infrastructure/shared/idempotency`（読み取りポートを application に置く ADR-0031 と同型の判断）。
- 記録の書き込みは**ユースケース自身のトランザクション内**で行う（ADR-0051 がユースケース＝トランザクション
  境界と定めている）。記録と業務書き込みが同一トランザクションに乗ることで、片方だけが commit される
  （「キーはあるがリソースが無い」「リソースはあるがキーが無い」）状態を避ける。

### `IdempotencyStore.claim` の 2 手（本決定でいちばん分かりにくい部分）

`JdbcIdempotencyStore.claim` は `INSERT ... ON CONFLICT (world_id, idempotency_key) DO NOTHING` に
続けて `SELECT ... FOR UPDATE` を発行する。2 文に分かれているのは、**直列化したい競合が 2 種類あり、
それぞれ別の機構が止めている**ため。

1. **`INSERT ... ON CONFLICT DO NOTHING`** は**初回同士**の並行を直列化する。まだ記録行が無い状態で
   同じキーの初回リクエストが同時に来ると、UNIQUE 索引（`(world_id, idempotency_key)`）が後続の
   `INSERT` を先行の commit までブロックする。挿入できなかった側は `DO NOTHING` で abort せず、
   後続の `SELECT` で先着の行を読みに回る。
2. **`SELECT ... FOR UPDATE`** は**前回の試行が失敗した後の再送同士**の並行を直列化する。記録行は
   既に commit 済み（`resource_id` が `NULL` のまま）なので、この場合 `INSERT` は誰も待たせない。
   直列化を担っているのは行ロックだけであり、これが無いと 2 本の再送が同時に実処理へ進んで二重に
   リソースを作ってしまう。

この 2 つはそれぞれ専用の並行テスト（`JockeyRegistrationConcurrencyTest` の 2 ケース）で個別に証明して
おり、**どちらか片方を外すと対応する方のテストだけが落ちる**（もう片方は緑のまま）。とくに
「初回同士」のテストは `FOR UPDATE` を外してもスレッド数を増やしても緑のままになる（記録行が無い
初回では `ON CONFLICT` だけで直列化が閉じているため）。**この意味で「初回だけの並行テスト」は
`FOR UPDATE` の非空振り確認には使えず、それが緑であることは `FOR UPDATE` について何も証明しない**。
本 ADR を読む後続の実装者は、`claim` の 2 文のどちらかを「重複している」と見て削る前に、この非対称を
思い出すこと。

## 標準からの逸脱（3 点）

1. **拠り所の IETF draft が Expired**。RFC 化されておらず、生きた標準ではない。Stripe / PayPal 等の
   実装が広く倣っているデファクトプラクティスとして採用する（前掲）。
2. **409 `idempotency-key-in-progress` を実装しない**。記録をユースケースと同一トランザクションで
   書くため、処理中の記録行は他トランザクションから見えない（draft が想定する「別トランザクションで
   即座に記録し、他リクエストがそれを見て 409 を返す」実装とは前提が異なる）。並行する再送は
   UNIQUE 索引でブロックされたのち、先行が確定した結果をそのまま読んで返す。クライアントから見ると
   「ブロックして正しい結果が返る」ほうが「409 を受けて自分で再試行する」より扱いやすく、こちらを
   選んだ。代償は待っているあいだ DB 接続を 1 本占有すること。これが実運用で痛むようであれば、
   `SELECT ... FOR UPDATE` を `FOR UPDATE NOWAIT` に変え、ロック競合を例外として捕まえて 409 へ
   倒すことができる（`claim` の変更で閉じる）。
3. **失敗レスポンスを再生しない**。本プロジェクトは業務エラーを `Result` の `Err` として返す設計
   （error-handling.md）で、業務エラー時もユースケースのトランザクションは commit される。エラー
   レスポンスの再生には失敗時のレスポンス本文そのものを保存する必要があり、本試作のスコープを
   超える。再送すると実処理が再実行され、同じ入力からは決定的に同じ業務エラーが再現する。

## 既知の限界

記録の `resource_id` が非 NULL でも、対応する集約が既に無い（記録だけが残り、集約を消す別経路が
記録を連動して消さない、等）場合がありうる。この場合 `findById` は `null` を返し、ユースケースは
失敗にせず**再登録**する（`JockeyRegistrationUseCase` の `registerIdempotently`）。再登録すると
記録の `resource_id` は新しく作られた集約へ上書きされ、その時点で冪等キーは「同じリソースを指す」
という保証を失う。現状この経路は集約削除の機能が無いため到達不能だが、将来削除機能を足すときは
記録行も連動して扱うか、この仕様のまま許容するかを再検討すること。

## 適用範囲

**`POST /api/worlds/{worldId}/jockeys` の 1 本のみに適用する。** 残り 10 本の作成系エンドポイントと
カスタムメソッドへの横展開、および 11 本ぶんの重複ロジック（`claim` → 指紋照合 → 読み直し／記録という
定型手順）をどう畳むか（デコレータ／AOP／封筒を見る共通ヘルパ等）は、試作で実際の痛みを測ってから
別 Issue で決める。

## Consequences（結果・影響）

- **新設した層**: DB スキーマ `shared`（`shared.idempotency_record`）、`application.shared` /
  `infrastructure.shared` パッケージ。境界づけられたコンテキストの分離ルール（architecture.md）は
  `domain.shared` だけを共有カーネルとして例外扱いする実装だったが、**`shared` は 3 層すべてで
  共有カーネル扱いとする**ことを本決定で明示し、`ArchSupport.kt` の KDoc をこの実態に合わせて更新した
  （従来の KDoc は「domain 直下の共有カーネル」とだけ書いており、実装より狭い記述になっていた）。
- **試作時点では実クライアントが誰もヘッダを送らない**。フロントエンドの `client.ts` 等はまだ
  `Idempotency-Key` を付与しておらず、本決定は「受け口を作った」段階に留まる。ヘッダを付けない限り
  従来どおりの挙動と変わらないため、既存クライアントへの影響はない。
- 冪等キーの受け方・現状の適用範囲は `.claude/rules/api-design.md`「冪等キー（再送安全性）」に
  結論として反映した。
- **関連**: #713 / #739（`INSERT ... ON CONFLICT DO NOTHING` を UNIQUE 制約の裁定者にする手法の
  先例。`:provision` の並行実行対策と世界の作成・改名の並行実行対策で先に同じ手を使っている）、
  ADR-0021（リソース設計は AIP・エラー描画は RFC 9457 という系統の切り分け。AIP-155 不採用の
  判断根拠と同型）、ADR-0031（ドメイン概念でないポートを `application` 層に置く先例）、ADR-0051
  （ユースケース＝トランザクション境界。記録と業務書き込みの同一トランザクション化の前提）。
