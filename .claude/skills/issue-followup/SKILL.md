# issue-followup（作業の締めに Issue へ反映する）

**作業中に分かったことは、書き戻さなければ消える**。Issue 本文は着手前の理解で書かれており、実装を終えた
時点の理解とは必ずズレる。そのズレを次に読む人（＝将来の自分）へ渡すのがこの工程である。

PR をマージした直後に 1 回走らせる。気づいた都度ではなく締めに寄せるのは本線の作業を中断しないためで、
取りこぼしは工程 1 の固定の問いで防ぐ。

## 工程 1: 棚卸し（固定の問いを順に当てる）

**記憶を頼りに「何かあったかな」と振り返らない**。思い出せた分しか拾えず、毎回精度が変わる。次の 5 つを
順に当てる。当てはまらなければ「なし」と明示して次へ進む。

1. **着手した Issue の本文と実装の差** — 完了条件のうち満たせなかった項目はあるか。Issue が想定した手順と
   実際にやったことが食い違っていないか（「A の手当てが要る」と書かれていたが不要だった、等）
2. **意図的に先送りした / 暫定にした箇所** — とくに解除条件が外部イベント待ちのもの（上流の更新待ち等）。
   コードコメントにだけ書いて Issue に無いと、条件が満たされても誰も気づかない
3. **作業中の実測・知見で他所に効くもの** — 同じ構図の既存 Issue はないか。Issue 本文の「関連」節、同じ
   原因の別アラート・別コンテキストを当たる
4. **PR レビュー指摘のうち、その PR で直さなかったもの**
5. **本筋と無関係で PR に入れなかった副次的な発見**

## 工程 2: 振り分け

| 反映先 | 条件 |
| --- | --- |
| 既存 Issue にコメント | その Issue のスコープに収まる情報（判断材料・実測結果・状況の変化） |
| 新規 Issue を起票 | 独立して着手できる作業単位になっているもの |
| 破棄 | PR 本文・コードコメント・ADR に既にあり、Issue 側に無くても辿れるもの |

- **破棄は正当な選択肢**。Issue が増えること自体にコストがある。「一応起票しておく」で棚を埋めない。
- **起票の前に必ず既存 Issue を全文検索する**（`gh issue list --search "<keyword>" --state all`）。
  調べれば既にあった、は繰り返し起きている。

## 工程 3: 一括提示して承認を得る

反映先（`#n` または「新規」）/ 種別（コメント・起票）/ 要旨 / Priority（新規のみ）を表にして提示する。

**承認が下りるまで GitHub へ書き込まない**。ここで手が滑ると、取り消しに Issue の削除やコメント編集が要る。

## 工程 4: 実行と確認

- 既存 Issue へのコメント: `gh issue comment <n> --body-file <file>`（本文が長いときは `--body` を使わない）
- 新規 Issue: **issue-ops の B に従う**（作成 → Project #4 に追加 → Priority 設定を 1 セットで行う）
- 締める前に、起票した Issue が Project #4 に乗り Priority が付いていることを確認する

## よくある失敗

| 言い訳 | 実際 |
| --- | --- |
| 「PR 本文に書いたから十分」 | PR は閉じたら読まれない。Issue から辿れるかで判断する |
| 「コードコメントに残したから十分」 | 解除条件が外部イベント待ちなら、コメントは誰も見に行かない。Issue が要る |
| 「小さい作業だから反映するものは無い」 | 小さい作業ほど「ついでに見つけた」が拾われずに消える。5 つの問いは当てる |
| 「関連 Issue は相手が気づくはず」 | 気づかない。同じ構図の Issue には明示的にコメントする |
| 「あとでまとめて起票する」 | 締めの時点が最も詳細を覚えている。ここで出す |

## Red Flags

- 工程 1 を飛ばして「特に無かった」と結論している
- 既存 Issue を検索せずに新規起票しようとしている
- 承認を得る前に `gh issue create` / `gh issue comment` を打とうとしている
- 起票したが Project #4 への追加と Priority 設定をしていない
